## Summary

All five EXPECTED items are implemented and smoke S1–S3 pass (19 checks, 0 failures). No stubs. Domain suite (29 checks) and unit suite cover the keystone margin/packing/lifecycle paths. The margin engine, bin packing, and checkout live-rate wiring are correct for the single-recipient case. Findings below are one broken core flow (tracking refresh at the terminal stage), two consistency gaps in the margin ledger, and operational/recovery holes that the smoke and domain suites do not exercise.

## Findings

### Blocker

1. **`refreshTracking` is refused at SENT — the only stage where it matters.** `refreshTracking` (`labels.ts:280`) calls `loadShippedPackage`, which throws `DomainRuleError` when `pkg.stage === pkg.fulfillmentMethod.terminalStage` (`labels.ts:70-72`). For SHIPPED the terminal stage is `SENT` — the point at which the carrier has the package and tracking is the live operation. The guard message ("the carrier has it; labels can't change now") is correct for buy/void, but wrong for R-176 tracking refresh, whose entire purpose is post-handoff status. Smoke S3b and the domain suite both advance `westPkg` to SENT and assert that void and re-buy are refused — neither asserts `refreshTracking` at SENT, so the regression is unexercised. The route `label/track` then surfaces this as a 422/DomainRuleError instead of the carrier status. Fix: split the terminal-stage guard by operation (buy/void refuse at SENT; tracking refresh must require SENT-or-earlier with a PURCHASED shipment; validate can stay refused at SENT).

### Major

2. **Margin ledger diverges for merged SHIPPED packages.** `chargedCentsFor(pkg)` (`labels.ts:100-107`) sums each member recipient's frozen `deliveryFeeCents`. Each recipient's checkout fee was quoted on **that recipient's own lines' parcel plan** (`quoteRecipientShipping` → `planParcelsForLines` for the recipient's lines only). At label buy, `planParcelsForPackage` (`quotes.ts:145`) re-packs **all the package's lines** (every member) into one combined parcel set and `quoteShipping` prices that combined set. So for a package merged from two same-address recipients, `chargedCents = recipientA_quote_high + recipientB_quote_high` (two separate 1-parcel quotes) while `costCents` is the cheaper carrier's quote for the **2-parcel combined** shipment. `marginCents = chargedCents − costCents` is then neither the per-recipient spread nor the per-shipment spread — it conflates two different parcel plans. The P12 reconciliation view (UR-003 report) will show inflated or distorted margins for any merged SHIPPED package, with no way to tell the honest spread from the packing artifact. The status doc states "charge = frozen checkout snapshot, cost = what Shippo bills" as if the parcel plans always match; they match only when the package has exactly one recipient. Either quote the combined parcel set at checkout too (so the frozen fee reflects the merged shipment), or record the per-recipient charge and the combined cost as separate ledger fields with a computed-blend note — but right now the single `marginCents` column is misleading for the merged case.

3. **A stuck `PURCHASING` row permanently blocks retries with no recovery.** `buyLabel` creates the `Shipment` with `status: "PURCHASING"` (`labels.ts:146-156`) **before** calling `buyLabelTransaction`. The catch block (`labels.ts:210-219`) flips the row to `FAILED` on any thrown error — but a hard crash, fetch timeout where the promise never resolves, or process kill between the create and the update leaves the row `PURCHASING` indefinitely. The partial unique index `shipments_one_active_per_package` (`WHERE status IN ('PURCHASING','PURCHASED')`) then refuses every retry with "already has an active label — void it before buying again" — but there is no label to void (the void path requires `status === "PURCHASED"`). There is no sweeper, no `PURCHASING`-timeout cron, and no staff UI affordance to clear a stuck row. At crunch (5k packages, provider outages per risk #5) this is a manual-SQL-only recovery on the exact failure mode the spec calls out. Add a PURCHASING→FAILED sweep (a short TTL, e.g. 5 min) or a staff "force-fail stuck purchase" path gated by `fulfillment.manage`.

4. **Void refund status is not reconciled; a carrier-rejected void silently double-charges.** `voidLabel` treats any non-`ERROR` refund status as success and flips the row to `VOIDED` immediately (`labels.ts:238-249`). Shippo voids are asynchronous: a `QUEUED`/`PENDING` can later be rejected by the carrier (e.g. label already scanned into the network). The row is already `VOIDED`, the package can re-buy, and the org is billed for two labels. There is no follow-up to confirm the refund settled, no `voidedAt`-vs-`refundConfirmedAt` distinction, and no `label_void_rejected` event. The smoke S2b only asserts the happy-path `VOIDED` + event; the rejected-refund path is unexercised. At minimum, record `refundStatus` (already captured) on the row and add a sweeper that re-checks pending refunds and emits a `label_void_rejected` event + reverts the row to `PURCHASED` if Shippo ultimately declines.

### Minor

5. **`lastFailed` lookup can miss when the package has >5 shipments.** The package detail query takes `shipments: { take: 5 }` ordered desc (`page.tsx:46`). `PackageLabelActions` derives `lastFailed` from that slice (`label-actions.tsx:43`). A package with many voids/rebuys plus a failure can age the FAILED row out of the top 5, so the "Last attempt failed" panel disappears while a FAILED row still exists in the DB. Bump the take or filter `status: "FAILED"` into the query for the failed-row leg.

6. **Display-quote fan-out has no concurrency cap or rate-limit.** `quoteCheckoutShipping` (`shipping-quotes.ts:78-102`) `Promise.all`s one live Shippo call per recipient with no throttle. A 20-recipient checkout page fires 20 concurrent Shippo requests on every page load (and again on every reload triggered by the stale-total conflict UI). Shippo rate-limits per token; crunch-time traffic across many open carts can trip it, and a single page load can self-inflict a burst. Batch or cap concurrency (e.g. p-limit-style 3–5 in flight), and consider a short per-order quote cache for the display path.

7. **`ShippingQuote` rows accumulate with no GC.** `quoteShipping` writes a rate-lock row on every label buy and on every submit re-quote (`persist !== false`), with a 30-min `expiresAt`. The engine never reads stored quotes ("always prices fresh") and no sweeper deletes expired rows. Over a 5k-package season this is thousands of write-only JSONB rows per season that the P12 reconciliation view will have to filter. Add a purge cron (P11/P12 class) or stop persisting on the label-buy path (the order-scoped submit row is the real rate-lock; the package-scoped row is only used for the S1b smoke assertion).

8. **`GROUND_SERVICE_TOKENS` is a hardcode masquerading as a product decision.** `margin.ts:21-25` whitelists `fedex_ground`, `fedex_home_delivery`, `ups_ground`, `usps_priority`, `usps_ground_advantage`. If the org's negotiated account returns `fedex_2_day` (or any service outside this list) as the cheapest, `eligibleRates` returns empty and `quoteShipping` throws `ShippingUnavailableError("no ground-comparable services came back")` — the SHIPPED option is disabled at checkout for that address with no operator recourse. The merged plan flags this as open question #4; the code picks one answer and offers no settings toggle. Surface it as a `shipping.eligibleServiceTokens` setting (defaulted to the current list) so an operator can widen it without a code change.

9. **`destinationFor` fallback uses `lines[0]` without a documented invariant.** `labels.ts:82-96` picks `pkg.recipientAddress ?? pkg.lines[0]?.orderLine.recipient`. For a merged SHIPPED package this is safe only because the grouping key normalizes the address across members. If grouping ever splits on a finer key (e.g. a future per-recipient greeting split that re-merges two addresses), `lines[0]` silently picks one member's address for the whole label. Add an assertion that all member recipients share the normalized address, or derive the destination from the grouping key rather than a member row.

10. **`planParcels` first-fit can strand small items in oversized boxes.** Units are sorted descending by volume and `parcels.find` returns the first open parcel that dimensionally fits (`packing.ts:73-80`). Parcels are created in unit-processing order, so the first parcel is the largest box. A small unit arriving after the large box opened can land in it even when a smaller box would fit, wasting volume and over-rating the parcel. For rate quotes this is a cost-accuracy issue, not a correctness bug — but it interacts with finding #2: an over-rated combined parcel inflates `costCents`, which deflates `marginCents` for merged packages. Consider best-fit (smallest open parcel that fits) rather than first-fit.

11. **Two `p8_shipping` migration directories were visible to the glob (only one persists).** The glob returned both `20260729043501_p8_shipping/` and `20260729140000_p8_shipping/`; the directory listing shows only `20260729140000_p8_shipping`. If the earlier timestamped dir was ever applied to a dev DB and then deleted, the migration-guard hash set could drift on machines that still have the old `_prisma_migrations` row. Verify the `prisma_migrations` table on the smoke DB has no orphan `20260729043501` entry; if it does, the guard's "DB in sync" pass is hiding a real divergence.
