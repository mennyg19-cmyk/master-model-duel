## Findings

### Major

**M1. `pdf-lib` declared with a floating range — clean-code Dependency Discipline.**
`package.json:26` — `"pdf-lib": "^1.17.1"`. clean-code.mdc § Dependency Discipline: "Pin versions -- no floating ranges." Every other dependency in this file is pinned exactly (`next": "15.5.22"`, `react": "19.2.8"`, `@prisma/client": "6.19.3"`, …). `pdf-lib` is the only caret range. The ponytail ladder itself justifies the *addition* (no stdlib/native/existing dep covers PDF generation), so the dep is fine — only the version spec violates the rule. Fix scope: pin to an exact version (and regenerate the lockfile entry).

### Minor

**m1. `pdfText` helper duplicated across three files — clean-code duplicated logic.**
The ~20-line inflate + hex-decode helper is copy-pasted in `scripts/test-p7.mts:129`, `scripts/test-p7-domain.mts`, and `.scratch/smoke-db.mts:21`. clean-code.mdc § Abstraction Discipline (Rule of 2) calls for extraction at 2+ real call sites; this is 3 (two committed). The STATUS even calls it out ("duplicated in `test-p7*.mts` and `smoke-db.mts pdf-has`") but leaves it. A shared `scripts/lib/pdf-text.ts` would satisfy the rule without net line growth. Test-only code, so Minor.

**m2. Filing-order comparator duplicated — clean-code duplicated logic.**
`lib/packages/print-batches.ts:26` (`sortForFiling`: recipientName → orderNumber → id) and `lib/print/pdf.ts:101` (inline `packages.sort`: recipientName → orderNumber) implement the same filing sort over slightly different shapes. Two call sites, same intent — a shared generic comparator would consolidate. Minor.

**m3. `.env.example` is stale — workflow Security Basics.**
`lib/env-spec.ts` adds the `CRON_SECRET` entry (P7), but `.env.example` (header: "Generated by `npm run gen:env-example`") was not regenerated/committed and still ends at `BLOB_READ_WRITE_TOKEN`. workflow.mdc § Security Basics: "`.env.example` with placeholders for every secret." The source of truth has it; the committed example doesn't. Minor (the generator script fixes it in one run).

**m4. `reprintBatch` predecessor + package scan run outside the transaction — concurrency.**
`lib/packages/print-batches.ts:141-165` reads the scoped packages and the predecessor batch outside `prisma.$transaction`, then creates the new batch inside (168-184). Unlike `runNightlyPrintBatch`, there is no `pg_advisory_xact_lock`. Two concurrent reprints of the same scope can both read the same predecessor, both create a batch superseding it, and both file the same packages — forking the supersession chain (one parent, two children) and producing duplicate reprint batches. No stage mutation occurs (so the print-never-ships invariant holds), but the "latest batch" lookup becomes ambiguous. Minor (staff-initiated, low concurrency).

**m5. `runNightlyPrintBatch` creates `CronRun` outside the transaction — durability.**
`lib/packages/print-batches.ts:67` creates the `CronRun` row before the advisory-locked transaction. A crash between the create and the tx commit leaves an orphan `CronRun` with no `OK`/`FAILED` status. The tx itself is correct (FAILED is written on catch). Minor.

**m6. Cron bearer comparison is not constant-time — workflow Security Basics.**
`app/api/cron/nightly-print/route.ts:14` — `auth !== \`Bearer ${env.CRON_SECRET}\`` is a plain string compare. A timing side-channel on the secret is theoretically exposed. The rule set does not mandate constant-time comparison, and the risk is low (cron secret, low request rate); noted for completeness. Minor.

**m7. STATUS doc inaccuracies — anti-hallucination / doc accuracy.**
`.scratch/PHASE-P7-STATUS.md` (a) names the migration `20260729023014_p7_packages_print`; the actual migration directory is `20260729130000_p7_package_engine_live`. (b) The "Schema" bullet claims the P7 migration added `Package.groupingKey`/`greeting`/`version`, `PackageEvent`, and the `PackageStage` enum — those pre-exist from earlier phases; this migration only adds `channel`/`deliveryDay`, `PackageLine`, `PrintBatch`/`PrintBatchItem`, and the `PrintBatchTrigger` enum (verified against `migration.sql` + `schema.prisma` diff). Minor (status doc, not shipped code).

**m8. `loadFulfillmentSummary` loads all `printBatchItem` rows globally — efficiency.**
`lib/packages/fulfillment.ts:53` — `prisma.printBatchItem.findMany({ select: { packageId: true }, distinct: ["packageId"] })` has no season filter (the table has no `seasonId` column; it lives on `PrintBatch`). Every batched package across all seasons is loaded to build the `batched` set, then only open-season packages are checked against it. Correct (awaitingBatch only counts open-season packages), but unbounded memory as prior seasons accumulate. Minor.
