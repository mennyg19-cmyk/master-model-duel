## Major

### M1 — `ReportTabs` is a third copy of the tab-nav pattern that P11 already flagged as duplicated
`src/app/(admin)/admin/reports/reports-tabs.tsx:13-36` is character-identical in structure to `src/app/(admin)/admin/settings/settings-tabs.tsx:13-36` and `src/app/(admin)/admin/email/email-tabs.tsx:13-36`: the same `<nav aria-label="… sections" className="flex gap-1 overflow-x-auto border-b border-[var(--color-line)]" data-testid="…-tabs">` wrapper, the same `aria-current={tab.href === active ? 'page' : undefined}` pattern, and the same active/inactive class strings (`'border-b-2 border-[var(--color-brand)] px-3 py-2 text-sm font-medium text-[var(--color-brand)]'` vs `'px-3 py-2 text-sm text-[var(--color-ink-muted)] hover:text-[var(--color-ink)]'`). The `EmailTabs` header comment even says "Same shape as the settings tabs, because it is the same kind of hub," and `ReportTabs` repeats the same justification. The P11 review (m4) flagged the two-copy version and said a shared `<TabNav items={…} active={…} ariaLabel={…} testId={…} />` in `components/ui/` would retire both. P12 added a third copy instead of doing that, so the drift the prior review named is now locked in at three sites: every new admin hub that wants tabs copies the component again. `clean-code.mdc` names "duplicated UI — extract shared components" and "inconsistent patterns — pick one, apply everywhere." Three copies of a 36-line component is ~108 lines of duplicated UI; the only variation between them is the tab list, the `aria-label`, and the `data-testid`.

### M2 — `legacy-import.ts` is a 603-line god file with mixed sub-concerns
`src/lib/migration/legacy-import.ts` is 603 lines and owns twelve distinct functions spanning four sub-concerns that `clean-code.mdc` would split: (1) the run lifecycle — `dryRunLegacyImport` (79-137), `readLegacyRun`/`readLegacyRuns` (139-155), `discardLegacyImport` (189-212), `commitLegacyImport` (221-267); (2) the chunk engine — `commitChunk` (269-315), `finishRun` (324-365), `assignChunks` (551-561); (3) the verdict pipeline — `readVerdicts` (418-493), `groupOrders` (367-416), `countVerdicts` (563-570), `sourceTotal` (572-580); (4) customer matching — `findCustomersByName` (497-520), `findCustomersByPhone` (522-535), `findImportedReferences` (537-548); plus `mapLegacyRow` (158-187) and `refreshCounts` (583-602) which cross the lifecycle/verdict boundaries. `clean-code.mdc` splits "when >500 lines **or mixed concerns**" — this trips both. Each sub-concern is cohesive enough to be its own module (`legacy-import/dry-run.ts`, `legacy-import/commit.ts`, `legacy-import/matching.ts`, `legacy-import/counts.ts`), and the file's own header comment (lines 19-41) names three properties that map onto three of those four sub-concerns, which is the signal that the concerns are real and not just line-count artefacts. The sibling `address-cleanup.ts` (392 lines, single concern) is the contrast: it stays under both triggers.

## Minor

### m1 — `Figure` component duplicated three times in P12 pages with drifting props
Three P12 pages define a local `Figure` over the same `<Card><dt className="text-sm text-[var(--color-ink-muted)]">{label}</dt><dd className="mt-1 text-xl font-semibold" …>{value}</dd></Card>` shape:

- `src/app/(admin)/admin/reports/[seasonId]/page.tsx:149-156` — `{ label, value }`, no adornment.
- `src/app/(admin)/admin/reports/margin/page.tsx:118-138` — `{ label, value, note?, testId? }`, renders an optional warning-coloured `<p>` under the `<dd>` for the "unpriced parcels" caveat.
- `src/app/(admin)/admin/migration/[runId]/page.tsx:173-195` — `{ label, value, tone?, testId? }`, recolours the `<dd>` itself when `tone === 'warning'`.

`note` (margin) and `tone` (migration) are two prop shapes for the same concept — "an optional warning adornment on the figure" — and the two pages pick different ones. A fourth `Figure` exists in `src/app/(admin)/admin/fulfillment/page.tsx:186-203` (pre-P12) with a different body (`CardTitle`/`CardDescription` and an `amount`/`value` pair), so the name `Figure` is now overloaded across four sites with three shapes. `clean-code.mdc` names "duplicated UI — extract shared components" and "type/schema drift — centralize types, single source of truth." A single `<Figure label value note? tone? testId? />` in `components/ui/` (or a `reports/Figure.tsx` colocated with the reports pages) would retire the three P12 copies and fix the `note`/`tone` drift; the fulfillment variant is a different component and should be renamed rather than folded in.

### m2 — `addressProblem` and `STATE_CODE` duplicated between the legacy parser and the cleanup scanner, with different ZIP rules
`src/lib/migration/legacy-rows.ts:175-188` and `src/lib/migration/address-cleanup.ts:54-63, 257-263` both define `const STATE_CODE = /^[A-Z]{2}$/` and a function `addressProblem(address)` that checks empty `line1`, empty `city`, state against `STATE_CODE`, and ZIP against a five-digit pattern. They disagree on the ZIP rule:

- `legacy-rows.ts:186` — `if (!/^\d{5}$/.test(address.postalCode)) return 'The ZIP code is not five digits.';` (strict 5-digit)
- `address-cleanup.ts:261` — `if (!ZIP_CODE.test(address.postalCode.trim())) return 'The ZIP code is not five digits.';` where `ZIP_CODE = /^\d{5}(-\d{4})?$/` (accepts ZIP+4)

Same intent — "is this address deliverable as written" — two implementations, two rulesets. A row that arrives from the legacy export with a `12345-6789` ZIP is rejected by the parser (`INVALID`) but would pass the cleanup scanner's validator, so the same door is unreadable on the way in and clean on the way out. `clean-code.mdc` names "duplicated logic — pull into `lib/` helpers" and "inconsistent patterns — pick one, apply everywhere." A single `addressProblem(address)` in `src/lib/core/address.ts` (with the `STATE_CODE` constant next to it) would give the validator one home and one rule; the cleanup scanner's `needsReview`/`reviewNote` fallback is a separate concern that the shared validator should not absorb.

### m3 — `countedOrder` filter shape duplicated between `datasets.ts` and `season-performance.ts`
`src/lib/reports/datasets.ts:33-36` exports `const countedOrder = (seasonId: string) => ({ seasonId, status: { in: COUNTED_ORDER_STATUSES } })`, used four times in that file (lines 59, 62, 126, 129) and the same shape is inlined again at lines 250 and 268 for the lapsed-customers export. `src/lib/reports/season-performance.ts:139` defines `const countedOrder = { seasonId, status: { in: COUNTED_ORDER_STATUSES } }` inside `readSeasonDrilldown` (a plain const, because `seasonId` is closed over). `src/lib/reports/margin-report.ts:55` inlines the same filter a third way: `package: { order: { seasonId, status: { in: COUNTED_ORDER_STATUSES } } }`. Three spellings of "orders that count" — a function, a local const, and an inline literal — across three files that all import `COUNTED_ORDER_STATUSES` from the same source. `clean-code.mdc` names "duplicated logic — pull into `lib/` helpers." Exporting `countedOrderFilter(seasonId)` from `season-performance.ts` (next to `COUNTED_ORDER_STATUSES`, which is already the single source for the statuses) and using it from `datasets.ts` and `margin-report.ts` would give the filter one home; the `margin-report.ts` nesting (`package: { order: … }`) is a Prisma `where` fragment that the helper would return, not a reason to inline a different shape.

## Notes (not findings)

Borderline under the "if removing duplication adds more lines than it saves" clause — left as a note.
- `src/app/(admin)/admin/reports/exports/page.tsx:111-113` `formatBytes` is a one-liner used once on the same page. Single call site, no second use anywhere in `src/`. Not a finding until a second use appears.
- `src/lib/migration/address-cleanup.ts:341-344` `canonicalEmail` (strip `+alias` and dots for dedup) is a sibling to `normalizeEmail` in `src/lib/core/normalize.ts` (case/whitespace for storage). The cast is necessary because `LegacyImportRow.candidates` is `JsonValue`, not a typed array — the alternative is a schema-level typed JSON column. Not a finding.
