## Major

### M1 — Address-shape mapping duplicated across the shipping folder and beyond
The 6-column DB address shape (`addressLine1`/`addressLine2`/`addressCity`/`addressState`/`addressPostalCode`/`addressCountry`) is re-mapped to `ShippingAddress` (`{line1, line2, city, state, postalCode, country, name, phone}`) by hand in two places inside `shipping/`:

- `src/lib/shipping/quote-service.ts:226-240` — `destinationOf(subject)` builds a `ShippingAddress` from a `QuoteSubject.address` (which is itself a hand-flattened copy of the same 6 columns at `quote-service.ts:97-103`).
- `src/lib/shipping/address-check.ts:50-59` — `validatePackageAddress` builds a `ShippingAddress` from a `box`'s 6 columns.

The same 6-column → `{line1, line2, city, state, postalCode, country}` mapping is repeated in at least six other files outside `shipping/`: `src/lib/orders/cart.ts:192-197`, `src/lib/orders/grouping.ts:77-91` and `:104-114`, `src/lib/orders/staff-orders.ts:159-166`, `src/lib/orders/customer-orders.ts:190-197`, `src/lib/checkout/checkout-summary.ts:233-241`, `src/lib/fulfillment/package-board.ts:247-255`. The defaults drift silently: `country` is `?? 'US'` in `quote-service.ts:237` and `address-check.ts:57`, `?? ''` in `cart.ts`/`grouping.ts`/`staff-orders.ts`/`customer-orders.ts`/`checkout-summary.ts`/`package-board.ts`, and left `null` in the `QuoteSubject.address` type (`quote-service.ts:34-41`). `clean-code.mdc` names this exactly: "duplicated logic — pull into `lib/` helpers." A single `toShippingAddress(box | row): ShippingAddress` (or a shared `address-mapping.ts`) would collapse all eight call sites and make the `country` default one decision instead of three.

### M2 — DB-access pattern drift inside `shipping/`
`src/lib/shipping/quote-service.ts` takes `client: DbClient` as a parameter on every exported function (`quoteShippingBoxes`, `recordQuote`, and the private `quoteShipments`/`quoteOne`/`readBoxTypes`/`readItemDimensions`) — dependency-injected, testable. The other three files in the same folder import the `db` singleton directly: `src/lib/shipping/label-service.ts:7` (`db` used at `:169`, `:237`, `:293`, `:351` and via `compensate`), `src/lib/shipping/address-check.ts:5` (`db` used at `:25`, `:61`), `src/lib/shipping/carriage-view.ts:5` (`db` used at `:73`). `clean-code.mdc` Consistency: "one data-fetching pattern per project … every subsequent session follows established patterns, never introduces a competing one." The injected pattern is the newer and better one (the P8 quote engine needs it for transaction-scoped reads inside `claimParcels`); the other three files were written against the singleton and never converted.

## Minor

### m1 — Magic constant `453.59237` (grams per pound) duplicated with divergent precision
`src/lib/shipping/shippo-api.ts:30` defines `const GRAMS_PER_POUND = 453.59237` and uses it at `:219` with `.toFixed(2)` (carrier API wants 2 decimals). `src/components/admin/carriage-card.tsx:230-232` defines a local `gramsToPounds(grams)` that inlines the same literal `453.59237` with `.toFixed(1)` (display wants 1 decimal). Same physical fact, two homes, two precisions, no shared source. `core/money.ts` already centralizes `toCents`/`formatCents`/`sumCents` for exactly this reason (its own header comment: "two places for the answer to drift"); a sibling `core/units.ts` with `gramsToPounds(grams, decimals)` would dedupe.

### m2 — `ShippingAddress` built from a settings row by hand, defaults written twice
`src/lib/shipping/quote-service.ts:243-257` `readShipFromAddress()` reads the `shipping.origin` setting and re-shapes it into a `ShippingAddress`, applying `name || 'Shipping department'`, `line2 || null`, `country: 'US'`, `phone: origin.phone || null`. `src/lib/shipping/address-check.ts:50-59` does the same re-shaping from a `box` with `country: box.addressCountry ?? 'US'` and `phone: null`. The `|| 'Shipping department'` fallback and the `'US'` default are business decisions written out in two places; a `shippingAddressFrom(origin)` (settings) and `shippingAddressFrom(box)` (package) pair — or one mapper over a shared `{name, line1, line2, city, state, postalCode, country, phone}` input — would remove the drift. (This is the same concern as M1, scoped to the origin/box defaults rather than the column mapping.)

### m3 — `label-service.ts` is a 423-line file with mixed concerns
`src/lib/shipping/label-service.ts:1-423` is under the 500-line trigger but trips the "mixed concerns" trigger in `clean-code.mdc` (split when >500 lines **or mixed concerns**). It owns: label purchase (`buyLabelForPackage` + `claimParcels` + `compensate`), label void (`voidLabelForPackage`), tracking refresh (`refreshTrackingForPackage`), the `isLabelVoidable` predicate, the `ShippablePackage` read model (`readShippable`), and the `VOIDABLE_STAGES`/`ACTIVE_LABEL_STATUSES` constants. `voidLabelForPackage` and `refreshTrackingForPackage` share no code with `buyLabelForPackage` except the `db.package.findFirst({ where: { id, ...boardScopeWhere(seasonId) } })` lookup — which is itself repeated three times (`:169`, `:237`, `:292`) with three different `include` shapes. Splitting (e.g. `label-buy.ts` / `label-void.ts` / `label-track.ts`, with a shared `read-shippable.ts` for the lookup) would give each file one verb.

### m4 — `carrier` typed as `string` everywhere it could be a union
`src/lib/shipping/provider.ts:38` types `CarrierAccount.carrier` as `'FedEx' | 'UPS'`. Every other carrier field widens to `string`: `CarrierRate.carrier` (`provider.ts:54`), `ShippingOption.carrier` (`margin.ts:18`), `CarriageParcel.carrier` (`carriage-view.ts:22`), `CarriageQuoteOption.carrier` (`carriage-view.ts:39`), and the `CARRIERS` array in `local-provider.ts:35-39` (which only ever emits `'USPS' | 'FedEx' | 'UPS'`). The loose typing is defensible at the Shippo boundary (`rate.provider` is a free string), but inside the margin engine and the carriage view a `Carrier` union would let the compiler catch the `'FedEx'` vs `'Fedex'` casing drift that `local-provider.ts:75` papers over with `.toUpperCase()` and that the smoke test pins with exact string matches. `clean-code.mdc` names "type/schema drift — centralize types, single source of truth."

### m5 — `VOIDABLE_STAGES` private, `isLabelVoidable` exported, `carriage-view` re-derives the rule
`src/lib/shipping/label-service.ts:35` keeps `VOIDABLE_STAGES` private and exports `isLabelVoidable(stage)` (`:284`). `src/lib/shipping/carriage-view.ts:120-121` then computes `canVoid: isLabelVoidable(box.stage) && box.shipmentBoxes.some((parcel) => parcel.status === 'PURCHASED')` — the `'PURCHASED'` literal is hardcoded because `ACTIVE_LABEL_STATUSES` (`label-service.ts:38`) is also private. The two constants that define "can this box be cancelled right now" live in `label-service.ts` but the rule is applied in `carriage-view.ts` with one half re-written. Export `isActiveLabel(status)` alongside `isLabelVoidable(stage)`, or move both predicates and their constants to a small `label-status.ts` that both files import.

### m6 — `destinationOf` silently substitutes `'US'` for a missing country
`src/lib/shipping/quote-service.ts:237` — `country: subject.address.country ?? 'US'`. `src/lib/shipping/address-check.ts:43` — the completeness check only verifies `line1 && city && state && postalCode`, never `country`. A box whose `addressCountry` is null (the column is nullable per `grouping.ts:35`) is quoted and validated as domestic US with no signal to the caller. The same `'US'` default appears in `address-check.ts:57`. The default is a business decision, but it is undocumented and duplicated; an international box that lost its country field would be priced as domestic without any log or fallback flag. Either require `country` in `destinationOf` (fail to FALLBACK) or surface the default as a named constant with a comment.

### m7 — Double `recordQuote` per shipping box (checkout + buy)
`src/lib/orders/order-service.ts:444-450` calls `recordQuote(tx, { orderId, packageId, groupingKey, quote })` at checkout, writing a `ShippingQuote` row for the quote shown to the customer. `src/lib/shipping/label-service.ts:390` calls `recordQuote(tx, { orderId, packageId, quote })` again inside `claimParcels` at buy time, writing a second `ShippingQuote` row for the quote the label was actually bought against (rates may have moved). Both rows share the same `packageId`. `src/lib/shipping/carriage-view.ts:85-88` reads `orderBy: { requestedAt: 'desc' }, take: 1` (shows the buy-time quote); `scripts/smoke-p8.ts:105-108` reads `findFirstOrThrow({ where: { packageId } })` (gets the checkout-time quote, Prisma's default order is unspecified). The two readers pick different rows. Keeping both rows is arguably correct reconciliation, but the pattern drift — two writers, two readers, no shared "which row is canonical" rule — is the kind of silent disagreement `clean-code.mdc` Consistency is for. Either document that the latest `requestedAt` is always the canonical one (and have the smoke test read it that way), or stop writing the checkout row once a buy row exists.

## Notes (not findings)

- `src/lib/shipping/bin-packing.ts` is a clean, single-concern module (volume/weight bin packing with an explicit `FILL_FACTOR` and `ASSUMED_ITEM` constants and a documented "heaviest-first into the largest carton" fallback). The `parcelOf`/`expandUnits`/`fillLargestBoxes` split reads well and the pure-function shape lets `margin.ts` stay pure too.
- `src/lib/shipping/margin.ts` is correctly pure (no `db`, no `server-only`, no I/O) and the `combineParcelRates` → `planMargin` → `allocateCustomerPrice` split keeps the margin rule in one testable place. The `byCostThenName` tiebreaker comment ("a coin toss here would mean the screen and the purchase could disagree") is exactly the kind of non-obvious constraint comment `clean-code.mdc` asks for.
- `src/lib/shipping/shippo-api.ts` using raw `fetch` + Zod schemas instead of the Shippo SDK is consistent with the `ponytail.mdc` ladder (stdlib/existing-deps before a new package) and is documented at `:18-25`. The unit conversion (`inches`/`pounds`) is isolated to this file as the rule requires — only the constant leaks (m1).
- `src/lib/shipping/local-provider.ts` pricing as a deterministic function of weight + destination (not random) is documented at `:24-29` with the right reason ("a rate that changes on every page load cannot be checked against what was charged"). The `carrierIndex * 7` tiebreaker (`:127`) is a deliberate "no two carriers tie" choice, also documented.
- `src/lib/shipping/provider.ts` lazy `getShippingProvider()` singleton with the "a page that merely imports something from this folder must not have to be configured for shipping" comment (`:84-88`) is a good trade-off and is consistent with how the payment gateway is built.
- `src/lib/audit.ts` shipping action shapes (`shipping.label_purchased`/`label_voided`/`label_failed`/`tracking_refreshed`/`address_validated`) are declared in the `AuditDetails` map before any caller writes them, which is the audit-trail discipline the file's header documents. No shipping action carries the carrier's own transaction id (it lives on the `ShipmentBox`), matching the "money rows never carry the instrument" rule.
